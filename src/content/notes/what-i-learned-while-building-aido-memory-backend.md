今天在做 Aido 记忆系统 backend 的过程中，我明显感受到一件事：

很多后端概念平时背的时候都认识，但一旦真正开始拆模块、理分层、定目录，就会发现自己以前理解得还不够“工程化”。

这次我花时间重新梳理了几组概念：

- `Entity`
- `Repository`
- `DTO`
- `VO`
- `DDD`
- `DDD-lite`

它们单看都不陌生，但如果不把它们放回真实业务线里，很容易停留在“背定义”的状态。对我今天这个场景来说，真正重要的问题其实是：

> 当我在做 Aido 的记忆系统 backend 时，这些概念到底该怎么帮助我把代码组织得更清楚？

这篇文章就想把这个问题讲清楚。

## 我为什么会重新梳理这一套概念

今天做的是 Aido 记忆系统的 backend 端。

记忆模块和普通 CRUD 最大的不同在于，它不是一个非常扁平的表单接口，而是会逐步长出自己的业务规则：

- 偏好怎么存
- 记忆怎么抽取
- 记忆怎么更新
- 记忆和 planner / goal / review 这些能力之间怎么协作

这种时候，如果后端结构只是“Controller 调 Service，Service 再调 Mapper”，短期当然能跑，但后面业务一复杂，代码很容易全堆进 Service 层。

所以我今天最核心的学习，不是某个孤立名词，而是开始意识到：

> 后端分层不是为了好看，而是为了给未来复杂业务提前留出可扩展的边界。

## Entity 到底是什么

`Entity` 可以理解成业务领域里“可被唯一识别的对象”。

最常见的特点有几个：

- 一定有唯一主键 `id`
- 通常和数据库中的一张表对应
- 一条数据对应一个实体实例
- 既承载属性，也可以承载少量领域行为

如果放到 ORM 语境里看，它通常就是数据库映射类。

但今天我觉得最重要的不是“它映射表”这件事，而是要分清楚：

- **传统 ORM 里的 Entity**：很多时候只是属性容器
- **DDD 语境里的 Entity**：不仅有属性，也应该能封装一部分业务行为

比如一个“用户偏好记忆实体”，如果它只是字段集合，那它更像数据库映射对象；如果它开始拥有“更新偏好”“合并偏好”“校验状态”之类的行为，它就更接近领域实体。

## Repository 到底在解决什么

`Repository` 中文一般翻译成仓储。

它的核心作用不是“换个名字写 DAO”，而是：

> 把业务代码和底层数据库操作隔开。

也就是说，业务层不直接写 SQL，不直接关心 MySQL / Oracle / PostgreSQL 的差异，而是统一通过 Repository 操作实体或聚合。

它负责的事情通常包括：

- 增删改查
- 条件查询
- 分页查询
- 屏蔽底层数据库实现

你可以把它想成实体或聚合的“数据库存取门面”。

如果用最传统的分层来画，关系大概是这样：

```text
Controller -> Service
               |
               v
          Repository
               |
               v
             Entity
```

但如果放到 DDD 里，它的定位会更进一步：

- 传统 DAO / Mapper 更偏操作单张表
- DDD 的 Repository 更偏操作一个完整聚合

这个差别在今天看起来只是表述不同，但后面一旦业务线长大，差异就会很明显。

## DTO 为什么不能随手用 Entity 顶掉

`DTO` 全称是 `Data Transfer Object`，也就是数据传输对象。

它的存在不是为了多写几个类，而是因为“传输”和“持久化”本来就不是一回事。

如果前后端接口直接把 Entity 暴露出去，会有几个很现实的问题：

### 1. 安全问题

Entity 很可能带着很多内部字段，比如：

- 密码
- 手机号
- 内部状态字段
- 审计字段

这些东西不一定适合直接暴露给前端。

### 2. 数据冗余

前端很多时候只需要展示一部分内容，如果直接把完整 Entity 传出去，很容易浪费带宽，也让接口返回结构变得很重。

### 3. 接口和数据库强耦合

如果接口直接复用 Entity，那么数据库表结构一改，接口大概率就跟着一起动。长期来看，这会让后端演进变得非常痛苦。

### 4. 无法满足复杂组合数据

很多接口并不是“返回一张表”，而是：

- 多个 Entity 的组合
- 经过裁剪后的字段集
- 针对某个页面或某个接口定制的数据结构

这种场景里，DTO 是最自然的选择。

所以 DTO 的几个关键特征是：

- 没有业务逻辑
- 场景专属
- 字段可裁剪、可组合
- 不映射数据库
- 适合序列化传输

## VO 和 DTO 也不是一回事

这一点我觉得也值得单独拎出来。

很多时候大家会把 DTO 和 VO 混着说，但严格一点看，它们的语义还是不同：

- `DTO`：强调跨层传输
- `VO`：强调前端展示

你可以简单理解成：

- Entity：数据库里的持久化对象
- DTO：接口输入输出时的数据传输对象
- VO：最终给前端某个页面或组件看的展示对象

如果做一个非常简化的链路，大概像这样：

```text
前端请求 -> UserCreateDTO -> Controller
                            |
                            v
                         Service
                            |
                            v
                      UserEntity
                            |
                            v
                          数据库
```

返回时则可能是：

```text
数据库 -> Entity -> Repository -> Service
                              |
                              v
                        UserDetailDTO / VO
                              |
                              v
                          Controller -> 前端
```

## DDD 到底想解决什么

如果只用一句话总结，我现在会把 DDD 理解成：

> 先把业务搞懂，再决定代码应该怎么长。

它不是某种“写法更高级”的框架，而是一种建模和组织后端代码的思路。

DDD 想解决的核心问题其实非常具体：

> 所有业务逻辑最后都堆进 Service 层。

这几乎是大部分传统项目都会慢慢遇到的问题。

业务刚开始简单时，Controller + Service + Repository 足够好用；但一旦出现复杂规则、状态变化、跨对象协作，Service 往往会越来越胖，最后变成一个什么都知道、什么都要管的巨型类。

DDD 的核心思路，就是把这些业务逻辑重新往“领域对象”里收。

## DDD 的典型分层

DDD 常见的分层大概是这样：

```text
接口层（Interfaces）
应用层（Application）
领域层（Domain）
基础设施层（Infrastructure）
```

### 接口层

这一层负责：

- Controller
- DTO
- 参数校验

也就是和外部请求直接打交道的部分。

### 应用层

应用层最重要的一点是：

> 它负责编排业务流程，但不承载核心业务规则。

它像一个调度者，负责协调多个领域对象完成某个用例。

### 领域层

这是 DDD 的核心。

这一层里通常会放：

- 实体
- 值对象
- 聚合
- 领域服务
- 仓储接口

真正重要的业务规则，应该尽量收在这里。

### 基础设施层

这一层负责实现那些“和外部世界打交道”的能力，比如：

- 数据库
- 缓存
- 消息队列
- 第三方调用
- 外部 client

一个特别关键的原则是：

> 依赖方向应该从外层指向内层。

也就是说，领域层不应该反过来依赖基础设施层。

## DDD 里几个最关键的概念

### 1. 实体

这个前面已经讲过，但在 DDD 里它不只是表映射类，更应该是“有状态也有行为的业务对象”。

### 2. 值对象（Value Object）

值对象没有唯一标识，它只通过“值”来区分。

它通常具备几个特点：

- 不可变
- 没有生命周期
- 用来描述实体某个属性

常见例子有：

- 地址
- 金额
- 坐标

### 3. 聚合（Aggregate）和聚合根（Aggregate Root）

这是 DDD 里最重要、也最容易抽象化的概念。

简单理解：

- 聚合是一组相关实体和值对象组成的整体
- 聚合根是这个整体唯一的对外入口

外部对象不能随便直接操作聚合内部对象，只能通过聚合根进入。

举例：

- 订单聚合：聚合根是 `Order`
- 用户聚合：聚合根是 `User`

我觉得聚合最值得记住的不是定义，而是三个设计原则：

- 一个聚合就是一个事务边界
- 聚合之间尽量通过 ID 引用
- 聚合大小要适中，不要无限做大

### 4. 领域服务（Domain Service）

有些业务逻辑不天然属于某一个实体，而是需要多个对象一起协作，这时候就更适合放到领域服务里。

比如：

- 支付
- 库存扣减
- 多对象联合决策

### 5. 工厂（Factory）

当聚合对象创建过程比较复杂时，不建议在应用层到处 `new`，而是通过工厂封装创建逻辑。

## 放回 Aido Backend，这些概念该怎么落地

这是今天我觉得最有价值的部分。

因为真正重要的不是“DDD 是什么”，而是：

> Aido 当前的 backend 架构，到底该怎么逐步往更清晰的方向靠？

我今天的结论是：

### 1. 当前的 aido-backend 还不是 DDD

它本质上还是一个比较典型的 Spring Boot 多层分层项目，不是完整 DDD。

这并不代表它有问题，只是意味着我们在讨论目录结构和职责划分时，要先认清现状，而不是假装它已经是一个成熟领域模型项目。

### 2. AIService 更像 planner 业务线的应用服务

从职责上看，它不是一个底层工具类，而是在编排 planner 这条业务流程。

### 3. PreferenceMemoryService 更像 memory 业务线的应用服务

它的定位也更接近应用层，而不是领域层本身。

### 4. AgentClient 未来应该归到基础设施层

这一点我今天觉得特别清楚。

因为 `AgentClient` 本质上是在和外部系统交互，它不是领域模型的一部分，更不应该被误放进领域层。

如果按 DDD-lite 的角度看，它更适合归到：

- `infrastructure/client`

## 如果 memory 模块先做 DDD-lite，怎么组织会比较稳

如果只针对 memory 这条业务线先做 DDD-lite，我觉得一个很稳的结构是：

```text
com.aido.memory
  controller
  application
  domain
  infrastructure
```

这种组织方式的好处是：

- 不会一下子把整个项目改得很重
- 先在最复杂、最值得建模的模块试点
- memory 自己能开始长出领域边界

## 如果整个 agent 模块都做 DDD-lite，我更推荐什么结构

如果视角再放大一点，我更喜欢这种方式：

```text
com.aido.agent
  planner
    application
    dto
    controller

  memory
    application
    domain
    dto
    controller

  goal
    application
    dto
    controller

  review
    application
    dto
    controller

  shared
    infrastructure
      client
      config
      dto
    support
```

这是我今天觉得最适合“两个人维护、逐步演进”的版本。

原因有几个：

### 1. 最外层先按能力划分

先按：

- `planner`
- `memory`
- `goal`
- `review`

这种业务能力来拆，比一开始按全局 Application / Domain / Infrastructure 平铺更直观。

### 2. 每个能力内部再分层

这样不会把整个项目一下子做成一个特别重的 DDD 目录，而是保留足够的可读性。

### 3. memory 可以先拥有自己的 domain

因为 memory 的规则明显更复杂，所以它最适合先开始做领域建模。

而：

- planner
- goal
- review

在初期完全可以先只有：

- `application`
- `dto`
- `controller`

不必一上来就硬上完整领域层。

### 4. 共享基础设施统一收口

像 client、配置、共享 DTO 这类东西，统一放到：

```text
shared/infrastructure
```

会比散在各个业务目录里更稳。

## 我今天最大的收获

如果只让我总结一句，我会说：

> 后端分层真正的价值，不是把术语背对，而是当业务开始复杂时，你知道该把哪类职责放到哪一层。

今天重新梳理 Entity、Repository、DTO、VO 和 DDD-lite 之后，我更清楚了几件事：

- Entity 不只是表映射，还可能承载行为
- DTO 的价值在于隔离接口和数据库结构
- Repository 的意义在于隔离业务与持久化
- DDD 的关键不是“用不用这些名词”，而是业务逻辑不要全部堆进 Service
- Aido 现阶段最适合的不是完整 DDD，而是按业务线逐步做 DDD-lite

对我来说，这个认知比单纯学会一个名词要重要得多。

因为它直接决定了：

- 我接下来怎么继续拆 memory 模块
- Aido 的 backend 以后怎么长
- 哪些地方该坚持建模，哪些地方不必过度设计

这也是今天这轮开发学习里，最值钱的部分。
