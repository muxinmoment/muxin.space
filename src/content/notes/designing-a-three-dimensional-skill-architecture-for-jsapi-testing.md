## 起点：两个裸提示词

大概两个月前，我接手了 JSAPI 自动化测试项目的 Skill 建设。当时的"资产"很简单：两个 Markdown 文件——一个提示文档校验 Agent 怎么做事，另一个提示用例生成 Agent 怎么生成用例。不是 Skill 格式，没有 frontmatter，没有目录结构，没有任何架构概念。

它们能跑。但每次改一个环节就要小心翼翼检查另一个会不会受影响，边界模糊、职责缠绕。

两个月后，这套体系变成了一个包含 **三级作用域 + 五大流程分类 + 双维度等级管控** 的完整分层架构，覆盖了从源码分析到测试反馈修正的全链路。

这篇文章就是这套架构的设计复盘。

---

## 核心设计：三维分层模型

我想要的不是一个简单的"把文件分分类"的方案，而是能同时回答三个问题的框架：

1. **这个 Skill 谁可以用？** → 纵向作用域
2. **这个 Skill 放在哪？做什么的？** → 横向流程分类
3. **这个 Skill 质量达标吗？风险高吗？** → 双维度等级管控

于是就有了这个三维模型：

![三维分层架构全景](/images/jsapi-skill-spec/01-architecture-overview.svg)

三个维度不是独立存在的——就像一个立方体的长宽高，缺一维就会塌方。

---

### 维度一：纵向三级作用域

用公司的组织形式来理解最简单：

> L0 全局级 = 公司公共工具库（所有部门都能借） \
> L1 项目级 = 部门专业工具箱（测试组内部共享） \
> L2 包级 = 你的专属工具抽屉（只有你项目用）

具体到目录上：

| 层级 | 路径 | 用途 | 数量预期 |
|---|---|---|---|
| L0 全局 | `~/.config/opencode/skills/` | 跨项目通用能力（如代码范式挖掘） | 3-5 个 |
| L1 项目 | `.opencode/skills/` | 仓库全链路共享，**必须按流程分类** | 5-7 个 |
| L2 包级 | 子包 `.opencode/skills/` | 单包专属的细分能力 | 0-3 个 |

一个关键规则：**同名覆盖**。包级 Skill 和项目级同名时，包级生效。这意味着你可以在不改动项目级 Skill 的前提下，针对特定包做定制化改造——继承加覆盖，优雅且安全。

---

### 维度二：五大流程分类

这是这次设计的核心创新。分类不是拍脑袋分的，是完全对齐项目的核心数据流的：

![核心数据流](/images/jsapi-skill-spec/02-data-flow.svg)

五个分类形成了一个完整的流水线：

| 分类 | 角色 | 核心 Skill |
|---|---|---|
| 🔀 **workflow** | 总调度员——只分派任务，不亲自干活 | `full-pipeline` |
| 📋 **doc** | 质检员——检查文档合不合规 | `doc-validator` |
| 🧪 **usecase** | 生产员——按规格生成测试用例 | `usecase-generator` |
| ⚡ **execution** | 操作员——执行测试、收集结果 | `testkit-runner` |
| 🔄 **feedback** | 返工通道——查问题、改用例、修文档 | `usecase-calibrator` |

你可以想象成一个工厂：

> workflow = 车间调度员，每天早上拿着工单在各个工序之间派活
> doc/usecase/execution = 三道生产工序，各干各的
> feedback = 质检返工通道，不合格就回来修，直到通过为止

这种分类方式最大的好处是**边界不重叠**。你知道每个问题该找哪个 Skill、新增能力该放哪个分类——不用纠结、不会放错。

---

### 为什么 workflow 要独立出来？

一开始我纠结过这个问题：全流程编排不就是依次调用其他 Skill 吗，为什么需要一个独立的分类？

答案是：**调度逻辑本身就是一种能力**。

workflow 决定的是"什么时候调谁、参数怎么传、失败了怎么办、并行还是串行"——这些和具体怎么做文档校验、怎么做用例生成是完全不同层面的事。混在一起只会让业务 Skill 变臃肿、调度逻辑散落各处。

所以 workflow 的设计原则是「**薄核心，重调度**」：
- ✅ 按顺序调用下游 Skill
- ✅ 汇总结果、异常中断、参数透传
- ❌ 不亲自解析源码、不生成文档、不编写用例

---

### Skill 合并：少即是多

架构演进过程中，有两次关键的合并：

![Skill 合并优化](/images/jsapi-skill-spec/05-skill-merge.svg)

1. **doc 分类**：`jsapi-doc-extractor`（提取） + `doc-validator`（校验） → `doc-validator`
   - 原因：实际场景中文档由人工编写已存在，Skill 的核心工作就是校验合规性。拆成"提取+校验"两个环节是过度设计了。

2. **feedback 分类**：`test-report-parser`（解析） + `usecase-fixer`（修正） → `usecase-calibrator`
   - 原因：读报告→找偏差→改预期是一个连续动作，拆成两个 Skill 增加了不必要的调度开销和数据传递。

合并后项目级 Skill 从 8 个收缩到 6 个，能力不打折，但边界更清晰、调度更简洁。

## 维度三：双维度等级管控

光有分类还不够，还需要质量门禁和权限沙箱：

**成熟度分级（P0-P3）**：

| 等级 | 定位 | 示例 |
|---|---|---|
| **P0 核心** | 流水线核心依赖，缺失阻断主流程 | doc-validator |
| **P1 关键** | 高频使用的核心业务 | usecase-generator, full-pipeline, coverage-analyzer |
| **P2 效率** | 辅助提效，不影响主流程 | usecase-calibrator, testkit-runner |
| **P3 探索** | 实验性能力，随时可废弃 | 新点子尝鲜 |

**安全等级（Tier1-Tier4）**：

| 等级 | 定位 | 对应 Skill |
|---|---|---|
| Tier1 只读 | 仅读取文件，自动执行 | coverage-analyzer |
| Tier2 调度 | 只编排不执行，关键阶段可设确认 | full-pipeline |
| Tier3 监督 | 可写入指定目录，输出可回滚 | doc-validator, usecase-generator, usecase-calibrator |
| Tier4 自主 | 全权限操作 | testkit-runner（占位） |

Tier2 是专门为 full-pipeline 增设的——它不亲自修改文件，但调度逻辑本身有风险（比如并行阶段资源竞争、审批中断恢复），需要独立的权限模型。

## Skill 与 AGENTS.md：谁做什么？

另一个容易被忽略但极其重要的设计点——Skill 和 AGENTS.md 的分工：

![Skill 与 AGENTS.md 协作](/images/jsapi-skill-spec/03-skill-agents-collab.svg)

一句话总结：**Skill 负责怎么做事，AGENTS.md 负责做事的标准**。

举个例子：`usecase-generator` Skill 定义了"读取文档 → 解析参数 → 按规则生成用例 → 输出 JSON"的工作流，但「生成的用例必须符合什么格式」「边界值的最小最大取值范围」「返回值的校验粒度」这些标准，全部写在 `packages/api_usecases_json/AGENTS.md` 里。

这样做的好处是：标准变了只改 AGENTS.md，流程变了只改 Skill，互不干扰。而且每条规则只在一个地方出现，不存在"改了这边忘了那边"的问题。

## 单 Skill 目录结构

每个 Skill 的统一骨架：

![目录结构](/images/jsapi-skill-spec/04-directory-structure.svg)

- **SKILL.md** — 唯一入口，YAML Frontmatter + Markdown 正文
- **INDEX.md** — references 资源索引（≥3 个时必须加，不会被自动加载，需在 SKILL.md 中显式引用）
- **assets/** — 模板、Schema、配置
- **references/** — 详细规则、示例、踩坑记录
- **scripts/** — 可执行校验脚本

关键设计决策：**INDEX.md 和 references 不会自动注入上下文**。Agent 只在 SKILL.md 中显式说"去读某个文件"时才会加载。这样做既保证了信息可追溯，又避免了上下文污染。

![三个隐喻](/images/jsapi-skill-spec/06-metaphors.svg)

我还给自己搞了三个记忆锚点：

1. **🏢 三级作用域 = 公司工具层级**：公共工具→部门工具→个人工具，越往下越专属
2. **🏭 五大流程分类 = 工厂生产线**：调度员安排四道工序，质检返工形成闭环
3. **🎯 双维度管控 = 质量门禁 + 权限沙箱**：核心能力高标准，危险操作要确认

每次跟同事介绍这套架构，用这三个比喻基本一句话就能讲明白。

## 意外的收获：coverage-analyzer

v2 版本中最大的变化是 `coverage-analyzer`——它在设计之初只是 execution 分类里的一个占位备注，没想到后来成了最早完整实现的两个 Skill 之一。

它的工作很简单但很关键：**在用例生成和测试执行之间，逐 API 检查已经生成了哪些用例、覆盖了哪些场景，和 legacy-app 的 intCases 基准做对比**。如果某个 API 的场景覆盖不完整，就自动触发补齐。

把它放在 execution 分类下而不是 usecase 分类下，是因为它**不生成用例内容，只统计数据差异**——它告诉你"少了什么"，不替你写。这种边界感在 Skill 设计里非常重要：每个 Skill 只管自己那一亩三分地，能力不重叠。

目前 coverage-analyzer 已经处于 P1 评级待确认状态——功能完整、有参考基准、支持单 API 和批量模式，唯一缺的是一个正式的确认流程。

## 从占位到完整实现：full-pipeline 的升级之路

full-pipeline 的演进也很有意思。最初它只是一个占位目录，SKILL.md 里只有一句话：「这是总流程编排 Skill，待后续填充」。

现在它已经是一个 5 阶段完整工作流了：
1. **预计算**（提取缓存、准备上下文）
2. **文档校验 + Registry 更新**
3. **用例生成**
4. **覆盖检测 + 补齐**
5. **反馈校准**

而且做了几件"不简单"的事：同阶段多 API 可以并行跑（subagent 并行策略）、API 超过 10 个会分批处理防止超时、破坏性变更会暂停等人工确认。

这些能力放在业务 Skill 里都不合适——它们是纯调度逻辑，和"怎么校验文档""怎么生成用例"没有半毛钱关系。这就是为什么 workflow 必须独立分类。

## 演进过程：从 0 到 1 的关键节点

复盘整个设计过程，有几个关键决策我觉得值得记录：

**1. 先搭框架，再填内容**

我没有一上来就给所有分类创建 Skill。前两周只做了两件事：确定分类目录、把现有的两个 Skill 迁移到位。框架稳了再往里加东西。

**2. 能合并的绝不拆分**

一开始有人建议"每个功能都做成独立 Skill，组合起来灵活"。但实践告诉我：**Skill 的拆分成本不在写代码，而在调度和上下文管理**。每多一个 Skill，就多一层通信开销、多一个可能出错的地方。除非两个能力确实独立且复杂度都很高，否则合并优先。

**3. 回退条件前置**

规范里有一条："如果 3 个月内项目级 Skill 不超过 3 个，可以随时取消分类目录，铺平所有 Skill，迁移成本为零。"这不是给自己留后路，而是**约束自己不做过度设计**。如果分类的收益（查找方便、边界清晰）抵不过成本（多一层目录），那就果断回退。

## 写在最后

这套架构从两个裸提示词开始，到现在的三维分层模型，中间经历过 Skill 合并、分类调整、等级体系建立。它不是什么业界标准，但它**恰好解决了我们这个具体项目的具体问题**——我觉得这是做架构设计最好的状态。

如果你也在用 OpenCode（或类似的 Agent 框架）做多 Skill 协作的项目，希望这套分层思路能给你一些参考。也欢迎交流讨论。
