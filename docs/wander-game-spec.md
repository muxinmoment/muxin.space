# 漫游收集册：像素房间小游戏规范

> 版本：v0.1
> 状态：设计基线
> 适用范围：`/wander/` 像素 3D 漫游入口及其四条内容支线

## 1. 产品定位

漫游不是传统导航页，也不是与内容无关的小游戏集合。它是一个可探索的像素工作室：用户通过轻量互动发现内容，通过收集进度获得继续探索的理由。

核心体验：

> 进入房间 → 发现物件 → 完成一个短玩法 → 获得内容线索/碎片 → 进入支线 → 点亮房间

每次互动控制在 10–30 秒内，失败成本低，不设置强制注册、排行榜或复杂教程。

## 2. 设计原则

### 2.1 内容优先

小游戏必须服务于内容发现。每个玩法完成后，都要产生一个明确结果：内容预览、支线入口、收藏语句或房间状态变化。

### 2.2 轻量探索

用户可以只看房间、直接点击入口，也可以完成小游戏。小游戏是奖励探索，不是访问内容的门槛。

### 2.3 像素世界一致性

3D 场景、按钮、卡片、提示、徽章和反馈统一采用像素风语言：限定色板、硬边阴影、块面边框、短促转场、清晰层级。

### 2.4 可随时退出

所有小游戏必须支持跳过、重置和直接进入对应支线。用户离开页面后进度保存在当前浏览器，不依赖账号。

### 2.5 移动端优先兜底

触摸操作不能依赖 hover、精确拖拽或长按。3D 不可用时，小游戏转为 2D 面板；小游戏不可用时，保留文字目录。

## 3. 核心进度

四条支线对应四块像素碎片：

| key | 区域 | 内容 | 碎片色 |
| --- | --- | --- | --- |
| `anime` | 番剧书架 | 番剧记录 | 紫色 |
| `photo` | 照片墙 | 摄影记录 | 粉色 |
| `notes` | 书桌 | 支线随笔 | 金色 |
| `memo` | 收音机 | 小木电台 | 绿色 |

完成一个区域后：

- 标记该区域为已探索
- 获得对应碎片
- 记录最近足迹
- 解锁一条内容预览
- 点亮该区域的灯光或物件

完成四个区域后：

- 房间进入 `complete` 状态
- 窗户或中央墙面出现隐藏徽章
- 显示“房间已点亮”反馈
- 提供隐藏结局入口，但不影响正常浏览

## 4. 四个小游戏

### 4.1 番剧书架：整理书脊

**目标**：将 3–5 本像素书拖动或点击排序。

**交互**：

- 桌面端支持拖拽
- 移动端支持“点击书 → 点击目标位置”
- 正确放置时书本吸附并播放短反馈
- 错误放置只抖动，不扣血、不重置

**完成结果**：展示一条番剧记录摘要，并提供“进入番剧书架”。

**数据要求**：书本内容来自公开的漫游内容；没有足够内容时使用虚构标题，不编造真实评分或观看记录。

### 4.2 照片墙：找出画面细节

**目标**：在一张像素化照片或插画中找到 3 个可点击细节。

**交互**：

- 点击可疑区域，不要求像素级精确
- 命中后显示短标签，例如“光线”“人物”“构图”
- 误点不惩罚，最多显示轻微提示

**完成结果**：展示照片标题、拍摄/记录时间或一句短注释，并提供“进入照片墙”。

**隐私要求**：使用公开可发布的照片；涉及他人、地点或敏感信息时，使用脱敏版本。

### 4.3 书桌：拼出一句话

**目标**：把 4–6 个词块拼成一句完整短句。

**交互**：

- 点击词块加入句子，再次点击可移除
- 不设置倒计时
- 提供一个“换一组”或“跳过”按钮

**完成结果**：显示一句支线随笔摘录，并提供“打开支线随笔”。

**内容要求**：句子必须来自真实已发布内容或经确认的草稿，不在前端暴露未发布敏感内容。

### 4.4 收音机：调到正确频段

**目标**：通过拖动或左右按钮调节旋钮，使指针落在目标区间。

**交互**：

- 目标区间宽，保证 10–20 秒内可完成
- 移动端使用左右按钮，不强制旋钮拖拽
- 调中时出现灯光、波形或短文字反馈

**完成结果**：显示一段小木电台文字，提供“打开电台”。不默认播放音频，避免打扰和额外资源消耗。

## 5. 状态模型

小游戏状态统一采用以下生命周期：

```ts
type WanderGameState = {
  key: "anime" | "photo" | "notes" | "memo";
  status: "locked" | "available" | "completed";
  attempts: number;
  completedAt?: number;
};
```

建议使用独立存储键：

- `muxin-wander-games`：四个小游戏状态
- `muxin-wander-fragments`：已获得碎片
- `muxin-wander-complete`：是否完成全收集

存储原则：

- 只保存进度，不保存完整内容
- JSON 损坏时安全回退为空进度
- 限制 payload 大小和 key 数量
- 不把个人敏感信息写入 localStorage

## 6. 反馈规范

每次动作都应有即时反馈：

- 命中：颜色闪烁、像素粒子或物件轻微弹跳
- 完成：碎片飞向进度徽章，提示持续不超过 2 秒
- 错误：轻微抖动或颜色回退，不出现惩罚性红屏
- 已完成：入口显示“已探索”，可重复游玩但不重复计数

反馈必须支持 `prefers-reduced-motion`：减少动态时只保留颜色、文本和状态变化。

## 7. 性能与兼容性

- 3D 场景继续使用低分辨率内部渲染和可见区域暂停
- 单个小游戏不引入新的大型依赖
- 不使用物理引擎、实时后处理或长驻音频
- 3D 初始化失败时显示 2D 游戏入口，不影响页面其余内容
- 首屏核心交互应在移动端中端设备上保持可操作
- 小游戏资源按进入区域后再加载，不能阻塞文字目录

## 8. 页面结构

推荐结构：

1. 像素 3D 房间
2. 房间状态与四个像素入口
3. 当前小游戏面板或内容预览
4. 文字目录与键盘快捷键
5. 收集进度和隐藏结局提示

小游戏面板应优先在当前页面展开，避免每次互动都产生额外页面跳转。

## 9. 验收标准

### 功能

- 四个区域都能独立进入和完成
- 完成后正确记录进度并刷新房间状态
- 刷新页面后进度仍然存在
- 清空或损坏存储后页面正常回退
- 可跳过小游戏并直接进入内容

### 视觉

- 3D 场景和外围 UI 使用同一套像素色板
- 入口、提示、完成状态均有明确的块面层级
- 不出现普通圆角卡片与像素场景混用造成的割裂
- 时间场景变化不会破坏文字可读性

### 兼容性

- 桌面端支持鼠标和键盘
- 移动端支持触摸，不依赖 hover
- 减少动态效果时仍能完成全部任务
- 3D/WebGL 失败时仍可使用文字目录和 2D 玩法

## 10. 实施顺序

1. 先实现统一的进度模型和收集徽章
2. 完成“找物件 → 获得碎片 → 预览内容”的通用交互框架
3. 优先开发照片墙找不同，验证点击玩法
4. 开发收音机调频，验证拖动/按钮双模式
5. 开发书架整理和书桌拼句
6. 最后制作四块碎片合成的隐藏结局

第一阶段不追求小游戏数量，而追求一个完整闭环：

> 找到一个物件 → 完成一个玩法 → 获得一条内容线索 → 进度被房间记住。
